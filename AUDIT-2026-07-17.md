## April Punch List — Status Check (PERFORMANCE-FIXES.md)

DJ Crates is a Tauri v2 app (Rust backend in src-tauri/src/, React frontend, Python DSP helpers in scripts/) that mirrors ~/Music/CRATES/ into Serato's binary .crate format and runs a nightly/weekly headless pipeline via launchd. The core sync/tagging code is competently built (TLV encoding is tested, lofty panics are contained with catch_unwind, caches persist across runs), but every item on the 2026-04-28 PERFORMANCE-FIXES.md punch list is still open in source, and the installed binary (built 2026-04-24) predates the punch list itself. Operationally the system is in worse shape than the punch list knew: dj-daily has been hung on a deemix download for 16.5 days (no sync since June 30), the Spotify popularity enrichment has burned 4-30 hours per weekly run while producing zero successful lookups ever (all 6,500 cache entries are -1), and headless step output is discarded by `open -gW`, so none of this was visible in any log. The destructive non-atomic sync (#4) that already caused one data-loss incident is unchanged.

### Feature ideas

- Pre-sync crate snapshots with one-click restore: before every sync, zip Subcrates/ + database V2 + neworder.pref into ~/.dj-crates-tools/snapshots/ (rotate last 14). Turns the #4 failure mode from 'restore from a manual Export Backup' into a built-in undo — and the UI gets a 'Restore crates from <date>' picker.
- --headless doctor subcommand: a fast read-only health report — tracks missing BPM/key/cues, mojibake-suspect tags (the looks_mojibake heuristic doubles as a detector), popularity-cache coverage %, dead symlinks in PLAYLISTS/Edits, database V2 entries pointing at missing files, and age-of-last-successful run per stage. Run it at the end of dj-daily and push the one-line summary to WhatsApp/ntfy — the 16-day hang and the all-(-1) Spotify cache would both have been caught the next morning.
- Replace Spotify popularity with Deezer rank: the library is deemix-sourced, and Deezer's public /track API returns a 'rank' popularity metric with no OAuth and generous limits. Since the deemix TSV pipeline already knows each track's Deezer ID, enrichment becomes a keyed GET instead of a fuzzy text search — eliminating the not-found problem in #5 entirely.
- 'Fresh Crates' auto-crate: generate GENRES%%NEW THIS WEEK and NEW THIS MONTH crates from file mtimes during sync (zero extra IO — the scan already stats every file). As a DJ adding ~125 tracks/day, having new arrivals gig-ready in one crate without digging through genre folders is an instant workflow win.
- Serato History mining for set analytics: parse ~/Music/_Serato_/History/Sessions/*.session to tag tracks actually played in real sets (play count, last played, avg position in set), auto-build a 'Proven Bangers' smart crate, and export per-genre play stats. This dovetails directly with the Kory Jamaal Intel A&R tracker — real DJ-floor data on which Afrobeats/Amapiano/R&B tracks move a room is exactly the differentiator a data-A&R portfolio needs.
- Camelot key stage: add a 'detect-keys' pipeline step (keyfinder-cli or librosa chroma) writing TKEY + Serato-visible key for harmonic mixing across all 30K tracks; incremental by 'key tag missing' the same way autocue.py skips already-cued files.
- Fuzzy duplicate report: at 30K tracks across genre/decade folders, dupes are inevitable. A weekly report matching normalized artist|title (the spotify_key normalizer already exists at lib.rs:959) plus duration ±2s, listing bitrate/format of each copy so the lower-quality one can be pruned — surfaced in the UI with a preview-before-delete flow like prune.rs already uses.
- Pipeline lock + status file: a single ~/.dj-crates-tools/pipeline.lock (PID + stage + started-at) shared by dj-daily/dj-weekly/UI. Prevents the daily and weekly jobs (or a manual UI sync) from overlapping on Sundays, lets the UI show 'weekly run in progress: enrich-popularity 42%', and gives the doctor command a hang detector for free.

## Rust Core (lib.rs, headless.rs, Tauri config)

The Rust core of dj-crates-tools is a competent single-purpose engine: lib.rs (2,123 lines) hand-implements Serato's TLV binary formats (crate files, database V2, neworder.pref) with a genuinely careful byte-preserving db updater (SeratoDbUpdate) that even has real regression tests, plus library scanning, BPM normalization policy, Spotify enrichment, and the Tauri command/CLI bootstrap all in one file. The architecture is the main debt: lib.rs is a god-file with three near-identical scan loops, four copy-pasted TLV/UTF-16 walkers, and two divergent Spotify clients and two BPM-policy systems split across lib.rs/spotify.rs/tagging.rs. The highest risks are data-loss shaped and mostly already known but unfixed: the clean sync still wipes Subcrates before rebuilding (the exact failure that destroyed crates on 2026-04-28), database V2 is rewritten via truncate-then-write with errors discarded and a backup that goes stale after its first-ever creation, and a surrogate-pair decoding bug silently duplicates or skips db entries for non-BMP filenames. Operationally, every command runs synchronously on Tauri's main thread (freezing the UI), the Spotify token expires an hour into multi-hour enrich runs, and no stage is incremental, so the weekly pipeline burns 3-4 hours re-analyzing ~30K unchanged files. Overall health: solid format engineering undermined by missing atomicity/backup discipline and a month of uncommitted work sitting on a single git commit; the fixes are well understood (several are already spec'd in PERFORMANCE-FIXES.md) and mostly small-to-medium effort.

### Findings

#### [HIGH / large] No incremental mode — every pipeline stage re-reads/re-analyzes all 30K files (4-5h weekly runs)

`src-tauri/src/lib.rs:1230`

sync_to_serato lofty-parses every file every night (1230-1313), sanitize/fix-bpms/label-moods/downbeat-cue each do their own full walk, and the DSP stages re-decode audio that hasn't changed (PERFORMANCE-FIXES.md #3: ~125 new tracks/day vs 29,875 wasted re-analyses). The library.json cache (1431-1436) is written but never used to skip work. Build one shared library index keyed by path → (mtime, size, meta): on scan, only lofty-parse entries whose mtime/size changed; give headless subcommands --only-new/--since flags (dispatcher at headless.rs:77-87 currently takes no flags). This turns the 3-4h dj-weekly into minutes and makes re-enabling label-moods cheap.

#### [HIGH / medium] Clean sync wipes Subcrates before rebuild — interrupted run destroys all crates (known, still unfixed)

`src-tauri/src/lib.rs:1163`

sync_to_serato deletes every GENRES%%/PLAYLISTS%% .crate file at lines 1163-1178, then spends minutes doing energy analysis, db parsing, and a full 30K-file lofty scan (1181-1313) before rewriting crates at 1330-1352. Any kill/crash/power loss in that window leaves Subcrates empty — this already happened on 2026-04-28 (documented in PERFORMANCE-FIXES.md #4, which contains a ready-to-implement fix). Implement the staged swap: build all .crate files into Subcrates.tmp/, then fs::rename current → .bak, tmp → live, delete .bak. Additionally, take a timestamped zip of Subcrates + 'database V2' into ~/.dj-crates-tools/backups/ (retain ~14) at the top of every non-preview sync. headless.rs:114-124 hardcodes clean=true, so every nightly cron run is exposed.

#### [HIGH / small] database V2 rewritten via truncating File::create with ignored write errors and no backup

`src-tauri/src/lib.rs:1377`

In sync_to_serato, `if let Ok(mut file) = fs::File::create(&db_path) { let _ = file.write_all(&db_data); }` (1377-1379): File::create truncates the existing Serato database to zero bytes first, then the write result is discarded. A disk-full error or a kill mid-write silently destroys database V2 (analysis, added-dates, everything) and sync still reports success. Same pattern in update_serato_db at line 657 (`fs::write(db_path, out)` — non-atomic). Fix both: write to `database V2.tmp` in the same directory, fsync, then fs::rename over the original (atomic on APFS), and propagate errors into the Result instead of `let _`.

#### [HIGH / small] database V2.bak backup created only once ever, then permanently stale

`src-tauri/src/lib.rs:653`

update_serato_db backs up only `if !backup.exists()` (653-656). After the first-ever tagging run the .bak is frozen at that ancient state — months later it's useless for recovery, while giving false confidence. The sync append path (1354-1380) makes no backup at all. Replace with rotating dated backups (e.g. `database V2.bak.YYYYMMDD-HHMMSS`, keep last N, prune older) taken before each mutating write; a 30K-track db is only tens of MB so cost is negligible.

#### [HIGH / small] UTF-16 decoders drop surrogate pairs — emoji/non-BMP filenames cause duplicate db entries and silently skipped updates

`src-tauri/src/lib.rs:471`

extract_pfil_from_otrk (469-476) and parse_existing_db_paths (705-712) decode UTF-16BE one code unit at a time via char::from_u32, which returns None for surrogates (0xD800-0xDFFF) — so any char outside the BMP (e.g. '🔥' in a DJ edit filename) is silently dropped from the decoded path. encode_utf16be (289-296) writes correct surrogate pairs, so the round-trip never matches: parse_existing_db_paths misses the track → sync_to_serato appends a duplicate otrk EVERY sync (1293), growing the db and showing dupes in Serato; and update_serato_db lookups keyed by the real path (629-630) never match, so BPM/mood/rename updates are silently skipped for those tracks. Fix: decode with char::decode_utf16(iter of u16) in one shared helper; this also collapses the 4 copy-pasted decoders (452-482, 676-723, 830-844, tests 1900-1909).

#### [HIGH / small] All 16 commands are synchronous — heavy work blocks Tauri's main thread and freezes the UI

`src-tauri/src/lib.rs:1109`

Every command is a plain `#[tauri::command] fn` (sync_to_serato:1109, enrich_spotify_popularity:1570 which sleeps 400ms per track for potentially hours, generate_smart_crate:1652, plus everything in tagging/unsorted/prune). In Tauri v2, non-async commands execute on the main thread, blocking the event loop — the sync:progress events you emit can't render smoothly, and src/App.tsx:112 already carries a 'force a render tick so the sync screen paints before a heavy invoke' workaround. Fix is one line per command: `#[tauri::command(async)]` (they stay blocking fns but run on a worker pool), or convert to `async fn` + spawn_blocking. This is the single cheapest UX win in the codebase.

#### [HIGH / small] Spotify token never refreshed — multi-hour enrich runs fail 100% after the 1-hour expiry

`src-tauri/src/lib.rs:1592`

enrich_spotify_popularity fetches one client-credentials token (line 1592) and reuses it for the whole run. A cold run over 30K tracks at 400ms/request takes 3+ hours, but the token expires after 3600s — every request afterwards returns 401, which search_spotify_popularity (1083-1085) maps to Err, counted as `errors` (1625-1627) while still burning the 400ms sleep. #### [MEDIUM / small] Sync/db writes have no 'Serato is running' guard — nightly cron can race a live Serato session

`src-tauri/src/lib.rs:1441`

sync_to_serato rewrites Subcrates and database V2, and even fires a live UPDATE at Serato's master.sqlite (1441-1452), with no check that Serato DJ Pro is closed. Serato loads its db at startup and rewrites it on quit — if dj-daily's 10:00 sync runs while Serato is open (e.g. after a late-night set left running), Serato clobbers everything the pipeline wrote, or worse, both write conflicting crate files. Add a guard at the top of sync_to_serato and headless::run_subcommand: `pgrep -x 'Serato DJ Pro'` → abort with a clear error (cron log picks it up). ## Metadata & Tagging (tagging.rs, normalize.rs, convert.rs, spotify.rs)

The metadata/tagging layer (tagging.rs, normalize.rs, convert.rs, spotify.rs plus shared helpers in lib.rs) is well-engineered for a personal tool: defensive catch_unwind around known lofty panic cases, persistent caches in ~/.dj-crates-tools/, Serato database V2 write-back after every pass, and real unit tests on the BPM/mood decision logic. The biggest risks are operational: the Spotify integration has essentially no rate-limit handling and permanently caches transient failures (poisoning the artist-genre cache), long enrichment runs outlive the 1-hour OAuth token, and the detect-bpms subprocess can deadlock the whole cron pipeline on an undrained stderr pipe. Tag writes are non-atomic in-place rewrites of the audio files themselves, so a crash mid-write can corrupt a track, and the Serato DB safety backup is only ever taken once. There is no mojibake or Unicode-normalization handling anywhere, which quietly degrades Spotify matching and orphan classification for a library heavy in non-ASCII artist names (Afrobeats, Amapiano, Baile Funk). Credentials are not hardcoded, but the Spotify client secret sits in plaintext settings.json.

### Findings

#### [HIGH / medium] Tag writes are non-atomic in-place rewrites of the audio file — a crash mid-save can corrupt a track

`src-tauri/src/tagging.rs:251`

All writers call tagged.save_to_path(&path, WriteOptions::default()) directly on the original file (tagging.rs:251, 324, 757). lofty rewrites the file in place when the tag grows/shrinks (ID3v2 resize rewrites the audio payload after the header); if the process is killed mid-write — cron timeout, power loss, the same class of interruption that already destroyed the Subcrates once — the music file itself is truncated/corrupted, and unlike crates it cannot be rebuilt. With sanitize/fix-bpms/label-moods rewriting thousands of files per pipeline run, exposure is real. The three library-management modules are: unsorted.rs (classifies downloaded tracks by folder/filename/ID3/artist-alias/Spotify signals and moves them into CRATES/GENRES/... with genre tags rewritten), prune.rs (a one-shot hardcoded restructure that rescues/merges/demotes genre folders and archives non-Urban-AC material to ~/Music/_Archive/CRATES_removed_<ts>/), and cleanup.rs (merges Hip-Hop into Hip-Hop:Rap, reclassifies Unknown Genre orphans, and tidies loose files into General <Genre>/). Safety posture is decent at the file level — nothing is ever deleted (archive-not-rm, copy+delete only as cross-volume fallback), all moves are manifest-logged, and Serato's database V2 gets pfil rewrites with a backup. Correctness is weaker: the classifier has three real bugs (hyphenated folder names can never match, artist-alias canonical names don't exist in the real library, and bare substring matching misroutes tracks), and the GUI auto-applies every classification without review while permanently rewriting genre tags. The biggest structural gaps are that the "for undo" manifests have no undo implementation, the Serato DB backup is taken exactly once ever, and there is zero duplicate detection in a pipeline whose collision strategy is to silently accumulate "(1)" copies. Prune and cleanup are idempotent on re-run (sources vanish after the first pass); unsorted routing is idempotent only because the Unsorted folder empties out.

### Feature ideas

- Library-wide duplicate finder: hash-based (size + partial MD5, optionally chromaprint fingerprint for re-encodes) sweep across CRATES that groups dupes, keeps the highest-bitrate copy, archives the rest with a manifest, and rewrites Serato db pfil entries — directly attacks the ' (1)' accumulation from unique_dest.
- `--headless undo <manifest.json>` subcommand that replays any prune/cleanup/unsorted manifest in reverse (to→from, restore archived files, re-point Serato db) — turns the existing write-only manifests into real insurance.
- `--headless doctor` health check for the cron pipeline: diff database V2 pfil entries against the filesystem, list missing files, orphaned crate references, and empty crates, and exit nonzero so dj-daily can notify before a gig instead of after.
- Pre-gig snapshot command: zip Subcrates/ + database V2 to ~/Music/_Archive/serato_snapshot_<ts>.zip (rotating, keep N) — one keystroke of protection given the Subcrates wipe incident already happened once.
- Self-learning artist aliases: watch for manual re-files inside CRATES (FSEvents or a periodic diff of the moves manifest vs current location) and append confirmed artist→genre mappings to a user dictionary JSON that classify() consults before the hardcoded ARTIST_ALIASES — the alias table stops rotting.
- Review queue UI for low-confidence routings: instead of auto-filing 0.6-confidence tracks, land them in _REVIEW/_Pending and add a fast triage screen (play preview, one keystroke per genre) — 30K-library misfiles are far costlier than 20 seconds of triage.
- Serato session-history integration: parse ~/Music/_Serato_/History sessions to build 'played last 90 days' and 'never played' smart crates during sync — surfaces archive candidates and gig-ready rotation automatically.

## Ops & Scripts (cron, launchd, Python DSP)

The ops layer is a launchd-driven chain (com.koryjcampbell.dj-daily 10:00 daily, dj-weekly Sun 14:00 — crontab itself is empty) that wraps shell downloaders (crateadd/crateup/dmget/deemix) and the Tauri app's --headless subcommands, with librosa-based Python scripts in scripts/ doing the real DSP (Rust wraps detect_bpms.py and autocue.py rather than duplicating them — Python is canonical for audio analysis and should stay, but its genre-BPM tables are triplicated and drifting). Overall health: functionally rich but operationally brittle — the audit found dj-daily has been silently hung since Jun 30 (16 days, stuck deemix download with no timeout, launchd never re-fires while the old PID lives), there is zero failure/staleness alerting, no lock protection despite provable daily/weekly overlap against a non-atomic Subcrates wipe, a 116 MB unrotated log, no requirements.txt for the load-bearing .venv, Spotify secrets hardcoded in three scripts plus a token cache sitting unignored in the repo root, and essentially the entire app uncommitted since the single March 13 initial commit. The highest-leverage fixes are small: kill and watchdog the hung chain, invoke the binary directly instead of `open -gW` with exit-code checks and notifications, add a shared flock, and commit the repo after scrubbing secrets.

## Project Health (git, tests, CI, deps, docs)

dj-crates-tools is a Tauri v2 desktop app + headless CLI that mirrors a ~/Music/CRATES folder hierarchy into Serato DJ Pro's binary .crate format and runs a tagging/enrichment pipeline (BPM normalization, Spotify popularity, downbeat cues, mood labels) over a ~30K-track library via daily/weekly cron. The code itself is in decent shape — ~6,600 lines of purposeful Rust across 10 modules, 38 real unit tests, a settings UI, and a thoughtful self-authored punch list (PERFORMANCE-FIXES.md) — but the project's operational posture is the problem: four months of work sit uncommitted on top of a single pushed commit, the GitHub remote is public while two Python scripts contain hardcoded Spotify credentials and an un-gitignored token cache sits in the repo root, the documented non-atomic sync that once destroyed all crates still runs daily, and the cron wrappers use `open -gW` so no app output or exit code has ever reached the logs (verified: zero [headless] lines in ~/.dj-daily.log). Health verdict: strong engine, no seatbelts — the top five fixes are all about not losing work, crates, or credentials, and four of them are under an hour each.
